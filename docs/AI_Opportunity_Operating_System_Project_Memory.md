# AI Opportunity Operating System --- Project Memory

**Status:** Active concept / ready for V1 engineering\
**Date captured:** August 31, 2026\
**Purpose of this document:** Persistent project memory capturing the
ideas, decisions, architecture, constraints, agents, marketplace model,
transaction model, and implementation direction developed in the

------------------------------------------------------------------------

## 1. Origin and Core Problem

The project began with a practical objective: find a way to generate
meaningful revenue quickly, with low risk and very little starting
capital.

The initial discussion considered:

-   Turning approximately \$500 into more capital.
-   Crypto trading and divergence-based strategies.
-   Using existing professional skills to generate revenue.
-   Digital marketing, analytics, website/app development, AI
    automation, and business process services.
-   The problem that conventional marketing takes time.
-   The need to find people who have an **urgent, existing need** rather
    than build demand through a long marketing funnel.
-   The observation that money changes hands continuously around the
    world and that AI may be able to identify and participate in
    existing flows of economic value much faster than conventional
    business-development methods.

This evolved beyond finding consulting work.

The central insight became:

> **Continuously find places in the economy where value can be created
> and captured.**

The system should not be restricted to a particular company, profession,
product category, industry, or conventional marketplace.

------------------------------------------------------------------------

## 2. Core Vision

Build a **general-purpose AI Opportunity Operating System** /
**autonomous economic matching engine**.

Its purpose is to continuously search the observable economy for:

-   unmet demand;
-   underutilized supply;
-   urgent needs;
-   scarce products or services;
-   pricing mismatches;
-   geographic mismatches;
-   timing mismatches;
-   information mismatches;
-   fulfillment gaps;
-   coordination problems; and
-   other lawful economic imbalances.

It should determine whether an imbalance can be profitably and lawfully
resolved, identify the best role for the system to play, and coordinate
the transaction.

### Core operating loop

**Discover demand → discover supply → normalize → classify → match →
research → score → calculate economics → assess risk → select
transaction role → prepare negotiation → obtain approval where required
→ negotiate → payment → fulfillment/logistics → settlement → follow-up →
learn.**

The system is designed around **economic opportunity itself**, not
around a predefined industry.

------------------------------------------------------------------------

## 3. Foundational Principle: Capital-Light Value Intermediation

The system should **not default to purchasing an underlying asset**.

Its default question should be:

> **What is the most capital-efficient, lowest-risk, fastest, and most
> profitable lawful role we can play in completing this transaction
> while creating meaningful value for the participants?**

Possible roles include:

-   intermediary;
-   referral source;
-   broker where legally permitted;
-   sourcing agent;
-   service coordinator;
-   reseller;
-   affiliate;
-   contractor;
-   marketplace/operator;
-   buyer representative;
-   seller representative;
-   fulfillment coordinator;
-   transaction facilitator; or
-   simple buyer/seller connector earning a lawful fee.

Ownership of inventory is only one possible transaction structure.

### Excellence principle

The system should not merely insert itself into a transaction and
extract a spread.

> **Never merely capture a spread. Create or unlock enough value to
> justify the spread.**

Examples of value creation include:

-   finding something the buyer could not find;
-   finding a better price;
-   negotiating favorable terms;
-   reducing search time;
-   validating a seller;
-   reducing fraud risk;
-   arranging payment;
-   coordinating logistics;
-   accelerating delivery;
-   aggregating suppliers;
-   solving a difficult fulfillment problem;
-   simplifying a complicated transaction; and
-   reducing uncertainty.

The desired long-term identity is effectively an **AI economic
coordination company**.

## 5. V1 Capital and Opportunity Economics

### Available capital

Approximately **\$500** can be made available to the engine.

However:

> **\$0-capital opportunities have first priority.**

The system should strongly prefer capital-light structures such as
referral fees, coordination fees, commissions, sourcing fees, service
fees, affiliate fees, brokerage where permitted, and other structures
that do not require inventory ownership.

### Minimum opportunity size

There is **no lower dollar limit**.

Micro-opportunities are acceptable if expected profit is positive.

A very small opportunity can outrank a much larger one if it is:

-   highly automated;
-   nearly instantaneous;
-   low risk;
-   requires no capital;
-   has high probability of completion; and/or
-   is highly repeatable.

### Conceptual opportunity scoring

A useful conceptual model is:

``` text
Opportunity Score =
    Expected Net Profit
    × Probability of Completion
    × Payment Certainty
    × Repeatability
    × Speed-to-Cash
    × Customer Value Created
    ---------------------------------
    Capital Required
    × Time Required
    × Operational Friction
    × Fraud Risk
    × Legal/Compliance Risk
```

The exact formula should be calibrated empirically rather than
hard-coded permanently.

## 6. Demand-First Marketplace

A major product insight is that the marketplace should not behave only
like Amazon, eBay, Craigslist, or a traditional catalog.

The central public interface can begin with:

# What do you need?

**Tell us what you want. We'll find it.**

Instead of forcing people to search existing inventory, customers can
**declare demand** and authorize the system to search for them.

### Demand Specification

A buyer should be able to provide:

1.  **What they want**

    -   natural-language description;
    -   image/photo;
    -   URL;
    -   model/SKU;
    -   service description;
    -   or even a loosely expressed need.

2.  **How much they can pay**

    -   target price;
    -   maximum budget;
    -   flexible/fixed budget;
    -   whether delivery/fees must be included.

3.  **Quality sought**

    -   new/used;
    -   condition;
    -   brand;
    -   specifications;
    -   credentials;
    -   experience;
    -   warranty;
    -   ratings;
    -   or domain-specific quality requirements.

4.  **When they need it**

    -   immediately;
    -   today;
    -   tomorrow;
    -   by a specific date;
    -   recurring;
    -   flexible.

5.  **Why it is important**

    -   context behind the request;
    -   urgency;
    -   intended use;
    -   consequences of delay.

    This information should improve service and prioritization, **not be
    used to exploit vulnerability or urgency**.

6.  **How they can pay**

    -   card;
    -   ACH;
    -   supported crypto/stablecoin;
    -   invoice;
    -   purchase order;
    -   financing;
    -   other supported methods.

    Sensitive payment credentials should not be stored directly in the
    request.

7.  **Where/how they can receive it**

    -   shipping destination;
    -   pickup radius;
    -   service location;
    -   digital delivery;
    -   business location;
    -   other fulfillment method.

### Additional optional buyer constraints

-   What is non-negotiable?
-   What is flexible?
-   Are substitutes acceptable?
-   Would the buyer pay more for faster delivery?
-   Would the buyer wait for a significantly better price?
-   May agents negotiate?
-   What are the negotiation limits?

### Core product insight

Traditional marketplace:

**Supply → listing → hope a buyer finds it.**

This system:

**Demand → specification → agents search supply → match → negotiate →
fulfill.**

The marketplace can still expose existing inventory/opportunities, but
demand itself is a first-class economic object.

## 7. Opportunity Graph / System Memory

The system must have persistent memory.

An opportunity should **not disappear simply because the original
listing or request disappears**.

Every discovered demand signal, supply signal, match, opportunity,
negotiation, and transaction should become part of an **Opportunity
Graph**.

The graph should preserve:

-   demand;
-   supply;
-   identities/organizations where appropriate;
-   locations;
-   prices;
-   historical prices;
-   quality;
-   constraints;
-   availability;
-   urgency;
-   timestamps;
-   matches;
-   alternative matches;
-   logistics;
-   economics;
-   negotiations;
-   approvals;
-   payment status;
-   fulfillment status;
-   trust/risk signals;
-   transaction outcome; and
-   agent decisions.

Historical opportunities become valuable training and intelligence data.

Eventually the system should answer questions such as:

> What economic mismatches repeatedly occur?

> Which categories produce the fastest time-to-cash?

> Which sources produce the highest close rate?

> Which demand signals most strongly predict an actual purchase?

> Which transaction structures produce the best risk-adjusted return?

> Which suppliers repeatedly solve difficult requests?

Opportunities should be continuously refreshed.

Potential lifecycle states include:

``` text
DISCOVERED
   ↓
QUALIFIED
   ↓
MATCHED
   ↓
ECONOMICALLY_VALID
   ↓
AWAITING_APPROVAL
   ↓
NEGOTIATING
   ↓
AGREED
   ↓
FUNDED
   ↓
FULFILLING
   ↓
DELIVERED
   ↓
SETTLED
   ↓
CLOSED
```

Alternate states:

``` text
REJECTED
EXPIRED
UNAVAILABLE
RESERVED
FRAUD_REVIEW
DISPUTED
CANCELLED
FAILED
```

An expired/unavailable opportunity should generally be archived rather
than deleted.

If supply or demand becomes active again, the opportunity can
potentially be resurrected and re-matched.

Agents should be permitted to execute only explicitly authorized state
transitions.

## 10. Agent Architecture

At least **20 agent roles** have now been identified.

### 1. Demand / Intention Agent

Continuously searches permitted public/authorized sources for
expressions of demand or need.

Examples:

-   "I need a painter tomorrow."
-   "Looking for someone to deliver this."
-   "Need GA4 fixed tonight."
-   "Looking to buy this discontinued item."
-   "Need transportation tomorrow."

Its generalized question:

> **Who is expressing willingness to exchange money for something?**

### 2. Opportunity Collector Agent

Collects signals from multiple sources, normalizes them, removes
duplicates/noise, and creates standardized records.

### 3. Classification Agent

Determines what an opportunity represents:

-   product;
-   service;
-   transportation;
-   local labor;
-   professional service;
-   B2B;
-   digital;
-   industrial;
-   commodity;
-   etc.

### 4. Opportunity Scoring Agent

Scores opportunities according to:

-   urgency;
-   buyer intent;
-   expected net profit;
-   probability of close;
-   competition;
-   capital requirement;
-   risk;
-   time-to-cash;
-   repeatability;
-   payment certainty;
-   operational friction;
-   customer value.

### 5. Supply / Matching Agent

Finds products, people, service providers, inventory, capacity, or other
resources capable of satisfying demand.

### 6. Research / Intelligence Agent

Investigates promising opportunities:

-   counterparties;
-   pricing;
-   alternatives;
-   availability;
-   reputation;
-   market conditions;
-   historical pricing;
-   geography;
-   specifications;
-   relevant context.

### 7. Economics / Arbitrage Agent

Determines whether the opportunity actually makes money after:

-   acquisition;
-   labor;
-   shipping/logistics;
-   payment processing;
-   taxes where applicable;
-   platform fees;
-   financing;
-   returns;
-   expected losses;
-   risk.

### 8. Risk & Trust Agent

Evaluates:

-   scams;
-   suspicious counterparties;
-   prohibited transactions;
-   unrealistic pricing;
-   fraud;
-   compliance concerns;
-   unsafe transactions;
-   reputation.

### 9. Negotiation Agent

Negotiates within explicit authorization and guardrails:

-   price;
-   quantities;
-   timing;
-   scope;
-   delivery;
-   terms;
-   conditions.

V1 requires human approval before outbound negotiation.

### 10. Transaction / Payment Agent

Coordinates transaction creation and approved payment processes through
supported rails.

### 11. Logistics / Fulfillment Agent

Determines how value gets delivered:

-   shipping;
-   courier;
-   local delivery;
-   pickup;
-   digital fulfillment;
-   service scheduling;
-   freight;
-   other logistics.

It incorporates fulfillment cost/timing into transaction economics.

### 12. CRM / Follow-Up Agent

Tracks:

-   prospects;
-   counterparties;
-   conversations;
-   follow-ups;
-   next actions;
-   outcomes;
-   opportunities that need attention.

### 13. Portfolio / Mission Agent

Looks across all available opportunities and asks:

> **Given current capital, time, capabilities, risk, and available
> opportunities, what should the system pursue right now?**

It can produce a ranked mission list hourly/daily.

### 14. Learning / Strategy Agent

Studies results and continuously learns:

-   which sources produce revenue;
-   which categories perform best;
-   which signals predict purchases;
-   which negotiations work;
-   which suppliers perform;
-   which opportunities waste time;
-   how scoring should change.

### 15. Orchestrator Agent

Acts as the operational coordinator of the agent workforce.

Moves opportunities through the appropriate workflow and assigns tasks
to specialized agents.

### 16. Availability & Lifecycle Agent

Continuously verifies:

-   active;
-   changed;
-   reserved;
-   under negotiation;
-   sold;
-   fulfilled;
-   expired;
-   unavailable.

It updates pricing/availability and can resurrect previously inactive
opportunities.

### 17. Buyer Advocate / Intent Agent

Interviews/communicates with the buyer until the system understands the
request sufficiently to represent the buyer's interests.

Transforms human desire into an executable Demand Specification.

### 18. Approval & Control Agent

Routes proposed high-impact actions to the human operator.

V1 approval channels:

-   Telegram;
-   email.

Possible mobile approval card:

``` text
Buyer price: $875
Seller target: $540
Delivery: $85
Fees: $34
Expected net: $216
Deadline: Tomorrow
Risk: Low

Proposed action:
Negotiate with seller up to $560.

[APPROVE]
[REJECT]
[MODIFY]
[ASK ME]
```

### 19. Trust, Integrity & Anti-Gaming Agent

Protects the marketplace itself from manipulation.

Monitors for:

-   fake demand;
-   fake supply;
-   duplicate listings;
-   coordinated accounts;
-   artificial scarcity;
-   circular/self-dealing transactions;
-   fake reviews;
-   price manipulation;
-   collusion;
-   repeated cancellation abuse;
-   payment anomalies;
-   bot abuse;
-   Sybil attacks;
-   agent prompt injection;
-   attempts to manipulate opportunity scoring.

### 20. Marketplace Lifecycle Agent

Maintains the public-facing opportunity inventory and determines:

-   what is available;
-   what changed;
-   what is still actionable;
-   what should be surfaced publicly;
-   what should be archived;
-   what should be re-matched;
-   whether a better supplier now exists.

As implementation progresses, some of these logical agents may share
code/services while remaining conceptually separate.

## 12. Anti-Gaming and System Integrity

The architecture must assume that both humans and automated agents may
attempt to game the system.

Security and integrity are not add-ons.

Required concepts include:

-   identity/account reputation;
-   device/account behavioral signals where lawful;
-   duplicate detection;
-   source provenance;
-   evidence tracking;
-   anomaly detection;
-   transaction graph analysis;
-   velocity limits;
-   rate limiting;
-   adversarial input handling;
-   prompt-injection isolation;
-   role-based permissions;
-   least privilege;
-   signed internal actions;
-   approval thresholds;
-   fraud review;
-   reversible actions where possible;
-   immutable audit history;
-   counterparty reputation;
-   model confidence;
-   independent verification for high-risk claims.

### Immutable audit log

Every meaningful agent action should record:

-   what the agent observed;
-   evidence/source;
-   what it inferred;
-   confidence;
-   rule/policy applied;
-   action proposed;
-   action taken;
-   human approval if required;
-   model/version involved;
-   timestamp;
-   resulting state transition.

This creates accountability, debugging ability, training data, and
anti-manipulation evidence.

**Oh My Pi** can be used as the coding agent/builder.

provider.

### Front end

Preferred:

-   **React**
-   likely **Next.js**

### Architecture

Use:

-   microservices where justified;
-   edge functions where appropriate;
-   event-driven communication;
-   asynchronous workers;
-   durable workflows;
-   API-first services;
-   containerized deployment;
-   infrastructure abstraction.

Avoid unnecessary microservice fragmentation in the earliest prototype.
Logical service boundaries can exist before every service is physically
deployed independently.

## 17. Opportunity Graph

The Opportunity Graph can initially be represented relationally in
PostgreSQL.

Do **not** introduce a graph database simply because the concept is
called an Opportunity Graph.

Add a dedicated graph technology such as Neo4j only when actual
graph-query complexity and performance justify it.

Possible graph relationships:

``` text
Buyer → NEEDS → Demand
Seller → OFFERS → Supply
Supply → SATISFIES → Demand
Match → CREATES → Opportunity
Opportunity → USES → Logistics
Opportunity → REQUIRES → Payment
Opportunity → GENERATES → Fee
Agent → EVALUATED → Opportunity
Transaction → FULFILLS → Demand
Transaction → CONSUMES → Supply
```

## 18. AI / LLM Architecture

The system must be **model agnostic**.

Open-source models can be used heavily for:

-   classification;
-   extraction;
-   deduplication;
-   basic matching;
-   summarization;
-   routine scoring;
-   inexpensive high-volume work.

More capable proprietary models can be reserved for:

-   complex reasoning;
-   ambiguous negotiations;
-   difficult research;
-   multi-step transaction analysis;
-   high-value decisions.

### LLM Gateway

Individual agents should never be tightly hard-coded to a specific
provider.

Conceptual interface:

``` text
llm.complete(
    task="classify_opportunity",
    complexity="low",
    privacy="standard",
    latency="fast",
    budget="cheap"
)
```

The gateway selects the appropriate model according to:

-   capability;
-   price;
-   latency;
-   privacy;
-   context length;
-   modality;
-   reliability;
-   current availability.

The strategic advantage should reside in the **Opportunity Graph,
transaction data, orchestration, and learning loops**, not dependence on
one model.

## 21. Blockchain --- Appropriate Role

There is a legitimate case for blockchain, but **not for putting the
entire marketplace on-chain**.

Good potential uses:

-   programmable settlement;
-   progressive settlement;
-   transaction proofs;
-   milestone-based release;
-   escrow-like structures where legally appropriate;
-   immutable attestations;
-   ownership/rights records where appropriate;
-   multi-party settlement;
-   cross-border value movement where lawful.

Do **not** put ordinary user profiles, private commercial information,
search histories, agent reasoning, or routine database records on-chain.

PostgreSQL remains the primary operational database.

### Progressive settlement example

``` text
Buyer funds transaction
          ↓
Funds reserved
          ↓
Seller confirms item
          ↓
Inspection passes
          ↓
Carrier picks up
          ↓
Delivery verified
          ↓
Acceptance confirmed
          ↓
Settlement completes
```

Example \$20,000 transaction:

``` text
10% — order accepted
30% — inspection passes
30% — logistics pickup confirmed
25% — delivery confirmed
5%  — acceptance window closes
```

### Multi-party settlement example

``` text
Buyer pays $1,000

Seller ............. $700
Carrier ............ $150
Inspector ........... $50
Marketplace ......... $100
```

## 25. Philosophical / Strategic Thesis

Several ideas underpin the project.

### AI compresses organizational formation

A business can increasingly be conceived and staffed with a substantial
virtual workforce in hours rather than months.

This changes the economics of entrepreneurship.

### Immediate revenue is fundamentally a matching problem

Revenue cannot simply be manufactured without a willing counterparty.

However, AI can dramatically compress the time required to:

-   observe demand;
-   identify supply;
-   understand intent;
-   evaluate economics;
-   communicate;
-   negotiate;
-   coordinate fulfillment.

The practical objective is therefore to minimize:

> **Time from observable economic need → completed value exchange.**

### Money is already moving

The system does not need to create all demand itself.

People are already buying, selling, hiring, transporting, repairing,
sourcing, searching, negotiating, and solving problems every moment.

The opportunity is to identify **existing value streams** and remove
friction from them.

### Search for imbalances, not categories

Agents should not primarily ask:

> "What products should we flip?"

They should ask:

> **"Where is value bottlenecked right now?"**

And:

> **"Can we legally and reliably resolve that bottleneck while creating
> enough value to earn part of the resulting economic benefit?"**

## 33. Native Multi-Rail Settlement Architecture

**Fiat and blockchain settlement are native platform capabilities from the outset.**

Blockchain settlement is not merely a future experimental module.

The platform should have a unified **Settlement Service** with multiple interchangeable rails.

```text
Settlement Service
    |
    +-- Fiat
    |     +-- Card
    |     +-- ACH
    |     +-- Other approved fiat rails
    |
    +-- Stablecoin / Crypto
    |     +-- Wallet payments
    |     +-- Stablecoin settlement
    |     +-- Supported crypto rails
    |
    +-- Programmable Settlement
          +-- Escrow-like flows
          +-- Milestone releases
          +-- Conditional release
          +-- Multi-party splits
          +-- Progressive settlement
          +-- Auditable transaction state
```

The commercial transaction state machine should be **payment-rail agnostic**.

Business logic defines:

- who owes what;
- who should receive what;
- required milestones;
- required evidence;
- approvals;
- release conditions;
- refund/cancellation conditions;
- dispute state;
- final settlement.

The settlement layer determines how those requirements are implemented using the selected lawful rail.

This prevents card, ACH, stablecoin, or smart-contract-specific logic from becoming embedded throughout the marketplace.

## 34. Blockchain as a Native Transaction Capability

Blockchain should be a native feature specifically for:

- **settlement;**
- **escrow-like flows where legally appropriate;**
- **auditable transaction state;**
- **programmable release of funds;**
- **progressive/milestone settlement;**
- **multi-party settlement;**
- **cryptographic transaction proofs;**

Potential on-chain information can include:

- transaction identifiers;
- hashes of agreed terms;
- approval attestations;
- milestone attestations;
- inspection proofs/hashes;
- pickup proofs/hashes;
- delivery proofs/hashes;
- settlement events;
- release events.

### Example progressive settlement

```text
Transaction agreed
      ↓
Funds committed / reserved
      ↓

      ↓

      ↓

      ↓

      ↓

      ↓

```

The precise percentages and conditions are transaction-specific.

Agents should observe verified real-world events and propose/execute permitted state transitions according to authorization and settlement rules.

## 37. Token-Efficient Development and Session Architecture

Token efficiency and context-budget management are explicit operational requirements for this project.

The project should **not** be developed inside one continuously expanding chat/session. Each major domain, module, or phase should have its own scoped session with a deliberately small context.

### Structural Rules

- Split large project work into separate sessions/chats by module, bounded feature, or implementation phase.
- A fresh session should receive only the minimum project context required to complete its scope.
- Persistent facts, locked architectural decisions, contracts, and cross-session state should live in versioned memory/specification files rather than being repeatedly restated in chat.
- Each module session should produce artifacts that can be consumed by later sessions without replaying the full transcript.
- The main architecture/orchestration session should receive synthesized decisions and artifact references rather than raw sub-session history.

### Delegation Rules

Use scoped research/build agents or subagents when the execution environment supports them, especially for:

- research-heavy work;
- source discovery;
- file hunting;
- large searches;
- repetitive code generation;
- mechanical migrations;
- test generation;
- refactors;
- documentation extraction.

Subagents should receive explicit inputs, constraints, expected outputs, and token/output limits. Their return to the parent session should be a concise synthesis plus files/artifacts rather than raw tool transcripts.

### Raw Output Rules

- Do not dump large API responses, JSON payloads, logs, model lists, scrape results, or command output into conversational context.
- Persist raw machine output to files or databases.
- Query/filter it with jq, Python, SQL, or equivalent tools.
- Return only the records, fields, summaries, or errors required for the current decision.
- When a tool confirms a successful file write or edit, do not immediately re-read the entire file unless verification is required.
- Prefer diffs, line ranges, checksums, tests, or targeted queries over full-file rereads.

### Decision Efficiency

- Batch related architectural or product decisions whenever possible.
- Prefer a decision packet containing several bounded choices to serial one-question-per-turn exchanges.
- Record locked decisions immediately in the appropriate project artifact.
- Avoid repeatedly reopening settled architectural decisions unless new evidence materially changes them.

### Long-Running Jobs

Where the execution environment supports asynchronous/background processes:

- launch long-running renders, builds, test suites, crawls, imports, or media operations as jobs;
- capture job IDs/status outside conversational context;
- avoid tight polling loops;
- use event/webhook/completion notification mechanisms where available.

Where true background execution is unavailable, use the coarsest reasonable polling interval and avoid repeated verbose status output.

### Context Principle

> **Conversation is the control plane. Files, databases, source control, workflow state, and structured artifacts are the memory plane.**

The goal is to keep conversational context focused on decisions, synthesis, exceptions, and human judgment rather than treating chat history as the project database.
